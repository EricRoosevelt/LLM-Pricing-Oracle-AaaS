# v1.1 Industrialization Roadmap

## Current Read

This repository is no longer a toy demo. The routing core already has real value:

- Cost, latency, capacity, and capability are scored together in [app/services/pricing_engine.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/services/pricing_engine.py:77).
- The API contract is clean and small in [app/api/v1/router_endpoints.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/api/v1/router_endpoints.py:17).
- CI and regression coverage exist and currently pass.

The main gap is not "can it route?" but "can it be operated, governed, tuned, and trusted in production?"

## Recommended Release Positioning

Keep the next release as `v1.1.0`, not `v2.0.0`.

Reason:

- The current product boundary is still a routing oracle, not a full traffic gateway or control plane.
- The biggest missing pieces are production hardening and feedback loops, which fit a strong minor release.
- A future `v2.0.0` should be reserved for a bigger product expansion such as tenant control plane, policy management, and closed-loop learning.

Suggested release title:

`v1.1.0 - Production Hardening and Decision Intelligence`

## What "Industrialized" Should Mean For This Project

For this project, industrialization should mean:

- Routing decisions are versioned, explainable, and reproducible.
- Model configs can be managed safely without code edits or process restarts.
- Health data, audit data, and route outcomes form a measurable feedback loop.
- Multi-tenant security, quotas, and operational guardrails exist.
- Deployment is safe under multi-worker, multi-instance, and partial dependency failure conditions.

## P0 Workstream

These are the highest-leverage items for the next version.

### 1. Turn model config into a validated registry

Problem:

- Model metadata is loaded at import time in [app/services/pricing_engine.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/services/pricing_engine.py:11) and [app/services/latency_tracker.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/services/latency_tracker.py:15).
- `ACTIVE_MODELS` is materialized once at process startup in [app/services/pricing_engine.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/services/pricing_engine.py:64).
- Any pricing or provider change requires a deploy or restart.

Upgrade:

- Introduce a `ModelRegistry` service with typed config validation.
- Add config versioning and checksum tracking.
- Add safe reload support from file, object storage, or admin API.
- Reject invalid model config before it can affect live routing.

Why it matters:

- This is the difference between "editing JSON in repo" and "operating a live routing product."

### 2. Split probe loop from the API process

Problem:

- The latency probe worker is started inside FastAPI lifespan in [app/main.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/main.py:18).
- In a real deployment with multiple workers or replicas, every process will start its own probe loop.

Upgrade:

- Move probing into a dedicated worker process or scheduled job.
- Publish probe results to Redis or Postgres with source metadata and freshness.
- Keep the API service read-only for route decisions.

Why it matters:

- This avoids duplicated upstream calls, noisy metrics, and inconsistent health data across replicas.

### 3. Add route outcome feedback APIs

Problem:

- Audit currently records the request snapshot only in [app/services/auditor.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/services/auditor.py:7).
- The system does not learn whether the selected model actually succeeded, timed out, or blew the budget.

Upgrade:

- Add `POST /api/v1/route/outcome`.
- Let agents report final selected model, fallback count, latency, token usage, vendor error class, and final success state.
- Persist both decision-time data and execution-time outcomes.

Why it matters:

- Without this, `accuracy`, `latency`, and even cost assumptions stay mostly static.
- With this, the oracle becomes tunable from actual field performance.

### 4. Build tenant-aware auth and quota controls

Problem:

- API keys are stored as a static env dict in [app/core/config.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/core/config.py:14).
- Rate limiting is fixed at one coarse rule in [app/api/dependencies.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/api/dependencies.py:21).

Upgrade:

- Store hashed agent keys in the database.
- Add tenant, environment, and scope metadata to each key.
- Support per-tenant RPM, daily budget caps, and kill switches.
- Add key rotation and audit trail for key lifecycle events.

Why it matters:

- This is essential if the oracle will serve multiple agents, teams, or customers.

### 5. Make health and observability real

Problem:

- `/health` currently returns a static success response in [app/main.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/main.py:45).
- There are logs, but no metrics, SLOs, or dependency-aware readiness checks.

Upgrade:

- Separate `liveness` and `readiness`.
- Check Redis, database, config registry freshness, and probe freshness.
- Export Prometheus metrics and OpenTelemetry traces.
- Add route counters by tenant, model, provider, rejection reason, and fallback depth.

Why it matters:

- Operators need to know whether the service is alive, routable, degraded, or blind.

## P1 Workstream

These are the features that make the system feel like a practical routing product rather than a scoring demo.

### 1. Explainable routing

Add richer decision output:

- rejection reasons per filtered model
- decision policy version
- config version used for the decision
- freshness of latency and capacity inputs
- a human-readable top-choice explanation

This makes debugging and customer trust much easier.

### 2. Policy packs instead of ad hoc weights

Current request-level custom weights are useful, but production users usually want named policies:

- `cost_saver`
- `balanced_default`
- `low_latency`
- `reasoning_first`
- `safe_fallback`

Each policy should be versioned and centrally managed, not recreated by every caller.

### 3. Better audit schema

Right now the audit payload is mostly stored as one JSON snapshot. Keep the snapshot, but also normalize key dimensions:

- tenant_id
- agent_name
- request_id
- chosen_model_id
- final_model_id
- route_status
- fallback_count
- actual_latency_ms
- actual_cost_usd
- config_version

This will make dashboards and incident review much easier.

### 4. Shadow mode and route replay

Add two practical capabilities:

- shadow score alternative policies without affecting live responses
- replay historical requests against a new policy or config version

This is one of the most useful industrial features for safe tuning.

## P2 Workstream

These are strong upgrades, but they can wait until after the first hardening release.

### 1. Provider adapter abstraction

Define provider adapters for:

- probe request building
- error normalization
- token accounting normalization
- model metadata enrichment

This keeps future provider expansion from spreading vendor-specific logic everywhere.

### 2. Better token estimation

`estimate_tokens` in [app/services/token_estimator.py](/home/ericdongz2042/projects/llm-pricing-oracle/app/services/token_estimator.py:1) is a useful heuristic, but later versions should support:

- provider-specific tokenizer backtests
- language-aware calibration jobs
- route-time confidence intervals on cost estimates

### 3. Commercial controls

If the product may become customer-facing, add:

- monthly usage statements
- tenant budget windows
- service plan tiers
- route policy entitlements

## Suggested API Surface For v1.1

Keep the API small. A good `v1.1` surface would be:

- `POST /api/v1/route/optimize`
- `POST /api/v1/route/outcome`
- `GET /health/live`
- `GET /health/ready`
- `GET /api/v1/admin/models`
- `GET /api/v1/admin/policies`

If you want to stay disciplined, defer write-side admin endpoints until after the registry abstraction is solid.

## Suggested Delivery Order

### Phase 1

- extract model registry
- separate probe worker
- add readiness checks
- add route outcome ingestion

### Phase 2

- tenant-aware auth and quotas
- normalized audit schema
- metrics and tracing
- policy packs

### Phase 3

- shadow mode
- route replay
- tokenizer calibration
- provider adapter refactor

## Suggested Success Criteria

The next version should be considered successful only if it can demonstrate:

- live config changes without unsafe manual edits
- one clear source of truth for model metadata and scoring policy
- measurable route quality using real outcome feedback
- safe behavior under Redis or database degradation
- stable deployment under multi-worker or multi-instance runtime

## A Practical Product Direction

If you want the most realistic positioning, do not sell this as just a "pricing calculator."

Position it as:

`An LLM routing control service for agents: budget-aware, latency-aware, and failure-aware.`

That framing matches the strongest parts of the current codebase and gives you a natural path toward:

- policy governance
- tenant controls
- route analytics
- adaptive decision intelligence

## My Recommendation

If bandwidth is limited, build this exact `v1.1` scope:

1. model registry
2. dedicated probe worker
3. route outcome ingestion
4. readiness metrics and Prometheus
5. tenant auth plus quota enforcement

That combination will make the project feel substantially less like an MVP and much more like something a real team could run.
