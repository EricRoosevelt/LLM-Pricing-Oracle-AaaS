# 产品经理作品集项目页统一框架

> 用途：当我要求 Agent 为某个项目生成产品经理作品集页面时，必须按本文执行。
> 目标：让不同项目页呈现出一致、清晰、可信的产品思维，而不是每页各讲各的。
> 适用对象：产品经理求职、研究生/商学院/交互设计/创新管理申请、面试作品集、Notion 作品页。
> 最后更新：2026-06-04

## 0. Agent 执行原则

当用户说“用我的作品集框架写一个项目作品集”时，Agent 必须做到：

1. 先理解项目事实，再写作品集，不得凭空补用户量、收入、留存率、转化率、市场份额。
2. 页面必须统一使用本文的叙事顺序：**问题判断 -> 用户场景 -> 产品方案 -> 产品取舍 -> 交付证据 -> 复盘路线图**。
3. 所有事实必须能追溯到代码、文档、截图、测试结果、Notion 页面、GitHub、Figma、发布材料或用户提供的证据。
4. 如果某类证据没有，就明确写“待补”，并给出采样清单，不能包装成已完成。
5. 每个作品页都必须让招聘产品经理的人看到：用户是谁、痛点是什么、为什么值得做、怎么取舍、怎么验证、下一步怎么迭代。
6. 技术细节只能服务产品判断。API、代码、架构、测试可以出现，但不能压过产品叙事。

## 1. 开始前必须收集的信息

Agent 在正式写作前，应尽量通过只读方式收集以下材料。

### 1.1 项目基础信息

- 项目名称。
- 一句话定位。
- 项目类型：例如 Developer Tool、AI Infra、浏览器扩展、SaaS、数据产品、内容工具、内部工具。
- 目标用户。
- 用户使用场景。
- 我的角色。
- 项目阶段：概念验证、MVP、已上线、发布前、开源 demo、课程项目、个人项目。
- 交付形态：Notion、GitHub、Figma、Demo、API、Chrome extension、Web app、CLI、报告、商店物料等。

### 1.2 可验证证据

- GitHub 仓库或本地源码。
- README、PRD、roadmap、release note、help center、privacy policy。
- 测试结果、覆盖率、QA 矩阵、故障注入、性能证据。
- 设计稿、架构图、用户旅程图、截图、录屏。
- 商店物料、发布文案、竞品分析、用户访谈。
- Notion 页面、Figma 文件、FigJam 图、外部文档链接。

### 1.3 不足信息

如果缺少以下内容，必须在页面中标注“待补”或放入采样清单：

- 真实用户访谈。
- 竞品实机截图。
- 使用数据。
- 业务结果。
- 可用性测试。
- 正式上线证明。
- 产品指标体系。

## 2. 统一页面标题格式

所有项目页标题统一使用：

```text
项目名｜一句产品定位
```

示例：

```text
LLM Agent Routing Control Plane｜面向 AI Agent 的模型路由控制面
MD摘摘（MDZZ）｜跨 AI 对话站点的摘录、回溯与知识库沉淀工具
```

标题不要写成：

- 只有项目名。
- 只有技术名词。
- 太长的营销句。
- 与项目内容不匹配的旧标题。

## 3. 页面固定结构

每个作品页必须使用以下 10 个一级模块。模块名可以轻微本地化，但顺序不要随意改变。

```markdown
# 项目名｜一句产品定位

> 一句话说明：这个产品为谁，在什么场景下，解决什么问题。

## 1. 30 秒摘要
## 2. 为什么值得做
## 3. 目标用户与核心场景
## 4. 产品方案
## 5. 关键产品取舍
## 6. Demo / 交付形态
## 7. 验证与证据
## 8. 复盘与下一步
## 9. 面试讲述版本
## 10. 外部链接 / 附录
```

## 4. 模块写法规范

### 4.1 30 秒摘要

这一节是给招聘方快速判断项目价值的。必须包含表格。

模板：

```markdown
## 1. 30 秒摘要

| 维度 | 内容 |
| --- | --- |
| 项目类型 |  |
| 目标用户 |  |
| 我的角色 |  |
| 核心价值 |  |
| 当前阶段 |  |
| 关键结果 |  |
```

写法要求：

- “项目类型”要让人知道项目属于哪个产品领域。
- “目标用户”必须具体，不要只写“所有用户”。
- “我的角色”要写产品工作和交付工作，不要只写“开发者”。
- “核心价值”必须是用户价值或业务价值，不是技术栈。
- “关键结果”只能写可验证结果，例如 `17 passed`、`88.08% coverage`、`支持 16 个站点`、`已生成商店物料`。

禁止：

- 未验证的下载量、收入、留存率、转化率。
- “效果很好”“用户很喜欢”这类无证据表述。
- 只写技术栈，不写产品价值。

### 4.2 为什么值得做

这一节回答：为什么这是个值得产品化的问题，而不是个人兴趣或技术 demo。

必须包含：

- 用户现在怎么做。
- 现有方式有什么痛。
- 痛点为什么高频或重要。
- 如果不解决，会造成什么成本。
- 产品机会是什么。

推荐结构：

```markdown
## 2. 为什么值得做

当前用户在这个场景下通常会...

问题 1：
问题 2：
问题 3：

产品机会：
```

写法要求：

- 从用户行为写起，不从技术实现写起。
- 痛点要具体：成本、时间、风险、失败、重复劳动、不可治理、不可追踪、不可沉淀。
- 最后必须落到“产品机会”。

### 4.3 目标用户与核心场景

这一节回答：产品到底给谁用，在哪个场景下用。

必须包含：

- 目标用户画像。
- 高频使用场景。
- 当前替代方案。
- 用户成功完成任务的标准。

模板：

```markdown
## 3. 目标用户与核心场景

### 目标用户

- 用户 A：
- 用户 B：
- 用户 C：

### 核心场景

1. 场景一：
2. 场景二：
3. 场景三：

### 用户成功标准

-
```

写法要求：

- 如果是 Developer Tool，目标用户可以是开发者、Agent 团队、平台团队、内部工具团队。
- 如果是消费工具，目标用户要写行为画像，例如“同时使用多个 AI 站点的学习者”，不要只写“学生”。

### 4.4 产品方案

这一节回答：产品怎么解决问题。

必须包含：

- 核心闭环。
- 关键功能模块。
- 信息架构、用户流程或系统流程。
- 每个功能对应哪个痛点。

推荐写法：

```markdown
## 4. 产品方案

核心闭环：

```text
输入/触发 -> 处理 -> 决策/整理 -> 输出 -> 反馈/复盘
```

关键模块：

| 模块 | 解决的问题 | 用户可见价值 |
| --- | --- | --- |
|  |  |  |
```

写法要求：

- 先讲产品闭环，再讲模块。
- 技术架构图可以放，但必须解释用户价值。
- 如果有 Figma / FigJam / Mermaid 图，要链接到这一节。

### 4.5 关键产品取舍

这是最重要的 PM 能力展示区。每个项目必须写。

必须回答：

- 为什么做 A，不做 B。
- 为什么先做这个版本，不做更复杂版本。
- 为什么这个入口、这个数据边界、这个交付形态是合理的。
- 这些取舍如何降低风险或加快验证。

模板：

```markdown
## 5. 关键产品取舍

| 取舍 | 决策 | 理由 |
| --- | --- | --- |
| 范围取舍 |  |  |
| 架构取舍 |  |  |
| 用户体验取舍 |  |  |
| 隐私/权限取舍 |  |  |
| 验证取舍 |  |  |
```

示例：

- 为什么 LLM Routing Control Plane 不做代理网关：避免集中持有用户 vendor key，降低密钥风险。
- 为什么 MDZZ 不做通用网页剪藏：Notion / Obsidian / Glasp 已覆盖通用剪藏，MDZZ 应聚焦 AI 对话结构和原文回跳。
- 为什么先做 API 而不是 dashboard：目标用户是开发者，API 是最短集成路径。

### 4.6 Demo / 交付形态

这一节回答：面试官能看见什么、验证什么。

可以包含：

- 产品截图。
- API demo。
- FigJam / Figma。
- GitHub。
- Notion 页面。
- Chrome extension 截图。
- 商店物料。
- 架构图。

写法要求：

- Demo 要服务“可观察点”，不能只是堆截图。
- 技术细节过长时放折叠区或附录。
- API response、curl、JSON 不应该占据主叙事的核心篇幅。

模板：

```markdown
## 6. Demo / 交付形态

| 能力 | 交付物 | 面试官可观察点 |
| --- | --- | --- |
|  |  |  |
```

### 4.7 验证与证据

这一节回答：凭什么相信这个项目不是空想。

证据类型：

- 自动化测试。
- 覆盖率。
- QA 矩阵。
- 手工回归。
- Demo E2E。
- 故障注入。
- 性能验证。
- 发布物料。
- 竞品官方来源。
- 用户访谈或可用性测试。

模板：

```markdown
## 7. 验证与证据

| 验证项 | 结果 | 证据 |
| --- | --- | --- |
|  |  |  |
```

写法要求：

- 数据必须可追溯。
- 没有真实用户数据时，不要硬编增长指标。
- 工程测试也可以成为 PM 证据，但要说明它验证了什么产品风险。

### 4.8 复盘与下一步

这一节回答：你是否知道项目边界、风险和下一版优先级。

必须包含：

- 做对了什么。
- 当前边界。
- 风险。
- 下一版路线图。

模板：

```markdown
## 8. 复盘与下一步

### 做对的事

-

### 当前边界

-

### 下一步路线图

| 阶段 | 目标 |
| --- | --- |
| v1.1 |  |
| v1.2 |  |
| v1.3 |  |
```

写法要求：

- 不要写空泛复盘。
- 每个下一步都必须和当前证据或风险相关。

### 4.9 面试讲述版本

这一节用于训练表达。每页必须有。

必须包含：

- 30 秒版。
- 2 分钟版。
- 面试官可追问点。

模板：

```markdown
## 9. 面试讲述版本

### 30 秒版

...

### 2 分钟版

...

### 面试官可追问点

| 追问方向 | 可展开内容 |
| --- | --- |
| 产品能力 |  |
| 技术沟通 |  |
| 取舍判断 |  |
| 路线图 |  |
```

### 4.10 外部链接 / 附录

这一节收纳不适合放在主叙事里的长内容。

可以放：

- GitHub 链接。
- Figma / FigJam 链接。
- Notion 链接。
- API 详情。
- JSON response。
- 长竞品分析。
- 采样清单。
- 测试日志。
- 详细架构图。

原则：

- 主文讲判断，附录放细节。
- 主文不要被代码块淹没。

## 5. 三类项目的适配方式

### 5.1 Developer Tool / AI Infra 项目

重点突出：

- 用户是开发者或团队。
- 问题是成本、稳定性、治理、可观测性、集成效率。
- 产品方案要讲 API 契约、集成路径、fallback、权限边界。
- 验证证据可以是自动化测试、覆盖率、E2E demo、metrics。

必须避免：

- 变成纯后端接口说明。
- 大量 curl / JSON 压过产品判断。

### 5.2 消费工具 / 浏览器扩展项目

重点突出：

- 用户行为场景。
- 入口和主流程。
- 竞品替代方案。
- 隐私和权限边界。
- 多端或多平台适配风险。
- QA 和发布证据。

必须避免：

- 一上来放竞品大表，缺少产品故事。
- 只讲功能，不讲用户为什么需要。

### 5.3 内容 / 数据 / 分析类项目

重点突出：

- 信息需求。
- 决策场景。
- 数据来源。
- 输出格式。
- 使用者如何根据结果行动。
- 准确性、可解释性和更新机制。

必须避免：

- 只展示报告，不讲产品化能力。
- 只讲结论，不讲数据可信度。

## 6. 统一质量门槛

Agent 完成作品页后，必须自查以下项目。

### 6.1 首屏自查

- 标题是否是“项目名｜一句定位”。
- 第一段是否讲清楚产品为谁解决什么问题。
- 是否有 30 秒摘要表。
- 是否能在 1 分钟内看出项目类型、目标用户、我的角色、关键结果。

### 6.2 产品思维自查

- 是否有明确用户问题。
- 是否有目标用户和核心场景。
- 是否有关键产品取舍。
- 是否有“不做什么”。
- 是否说明当前边界和下一步。

### 6.3 证据自查

- 每个结果是否可追溯。
- 是否区分已完成和待补。
- 是否避免未验证增长数据。
- 是否说明测试或 QA 证据验证了什么风险。

### 6.4 表达自查

- 技术细节是否过长。
- 是否有面试讲述版本。
- 是否有可追问点。
- 是否存在旧项目文案串台。
- 是否不同项目页结构一致。

## 7. 禁写项

没有证据时，Agent 不得写：

- 下载量。
- 活跃用户数。
- 收入。
- 留存率。
- 转化率。
- 市场份额。
- 用户满意度。
- “用户很喜欢”。
- “已上线”。
- “已发布”。
- “企业正在使用”。
- “显著降低成本”。
- “大幅提升效率”。

如果用户想表达这些内容，必须先提供证据。否则只能写：

```text
待补：需要真实使用数据或用户验证。
```

## 8. 采样清单模板

如果证据不足，Agent 必须输出采样清单。

```markdown
## 待补采样清单

| 采样项 | 目的 | 最低要求 | 隐私注意 |
| --- | --- | --- | --- |
| 用户访谈 | 验证痛点 | 至少 5 位目标用户 | 不记录真实姓名和隐私内容 |
| 竞品截图 | 支撑竞品分析 | 每个竞品 2 张图 | 账号信息打码 |
| Demo 录屏 | 验证主流程 | 1 条完整任务链路 | 不展示 token |
| 测试结果 | 验证稳定性 | 自动化或手工测试记录 | 不上传敏感日志 |
| 发布证据 | 验证交付状态 | 商店截图、release note | 不写未发布为已发布 |
```

## 9. Agent 最终交付格式

当 Agent 为某项目生成作品页时，最终至少交付：

1. `portfolio.md` 或 Notion 页面正文。
2. `evidence-index.md`：证据来源表。
3. `sampling-checklist.md`：待补采样清单。
4. 如适用：`product-architecture.mmd`。
5. 如适用：`user-journey.mmd`。
6. 如适用：Figma / FigJam 链接。
7. 如适用：Notion 页面链接。

最终回复用户时，必须说明：

- 写到了哪里。
- 哪些页面或文件被创建。
- 哪些内容是已验证事实。
- 哪些内容仍需采样。
- 是否修改了原页面。

## 10. 标准提示词

用户以后可以直接把下面这段话给 Agent：

```text
请按照 docs/portfolio/product-manager-portfolio-case-framework.md 中的“产品经理作品集项目页统一框架”，为这个项目生成一份产品经理作品集页面。

要求：
1. 先只读分析项目事实和证据，不要编造未验证指标。
2. 页面必须包含：30 秒摘要、为什么值得做、目标用户与核心场景、产品方案、关键产品取舍、Demo/交付形态、验证与证据、复盘与下一步、面试讲述版本、外部链接/附录。
3. 技术细节只能服务产品判断，过长 API/代码/日志放附录。
4. 明确区分已完成、待补和推测。
5. 输出 evidence-index 和 sampling-checklist。
6. 如果能用 Notion / Figma，就生成对应页面或图；不能用时，保留 Markdown / Mermaid 备份。
```

- 第一份短页适合作为主结构基础。
- 第二份长页里的 curl、JSON、完整 API demo 应移动到附录。

## 13. 最终判断标准

一页作品集合格，必须让招聘产品经理的人看完后能回答：

1. 这个项目解决谁的什么问题？
2. 为什么这个问题值得做？
3. 你负责了什么？
4. 你做了哪些关键产品取舍？
5. 产品闭环是什么？
6. 怎么验证它不是空想？
